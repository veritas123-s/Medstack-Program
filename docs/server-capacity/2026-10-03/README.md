# 医栈通服务器压力测试报告

测试日期：2026-10-03，北京时间。硬件：2 核 CPU、2 GiB 内存、5 Mbps 公网带宽，Windows Server 2025。测试时后台版本 5.1.0、Node v24.21.0；这是当日记录，不代表后来版本的容量。

**初步按 80–100 名持续编辑并同步的活跃用户规划。** 这个区间来自内部实测与带宽计算，公网业务的精确人数上限尚未测得。内部 200 模拟用户完成约 61 秒持续测试，400 用户出现明显排队。

## 业务负载实测

在同一台服务器启动独立后台进程和全新合成数据库，仅监听回环地址；认证与限流保持启用。400 个合成账号，每份文档含 160 条任务、90,749 字节。每用户约 1 请求/秒，循环执行读取同步文档、检查会话、读取文档、写入文档，每 4 秒写入一次。不同有效模拟 IP 表示不同出口，无法代表校园共享出口。

| 模拟用户 | 请求/秒 | 中位响应 ms | P95 ms | P99 ms | 错误 | 全机 CPU | 最低空闲内存 MB |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 9.4 | 5 | 9 | 31 | 0 | 7% | 290 |
| 25 | 23.5 | 4 | 8 | 50 | 0 | 10.2% | 255 |
| 50 | 46.9 | 4 | 25 | 78 | 0 | 12.7% | 216 |
| 100 | 93.8 | 8 | 63 | 100 | 0 | 23.9% | 157 |
| 200 | 187.4 | 29 | 607 | 770 | 0 | 41.4% | 141 |
| 400 | 255 | 1114 | 2633 | 2870 | 0 | 50.3% | 162 |

P95 表示 95% 请求的响应时间不超过该值。每档约 17 秒；400 用户档约 18.9 秒，P95 超过本次 1 秒阈值，结束继续加压。零错误仍可能伴随不可接受的排队延迟。

**200 用户持续测试：** 60.9 秒、11,919 次请求、195.7 请求/秒、零错误；P50 74 ms、P95 633 ms、P99 1090 ms，平均全机 CPU 43.3%、最低空闲内存 270 MB。该轮生产健康检查全部成功，最大耗时 142 ms。分级测试中的生产健康检查最大耗时为 704 ms。分级、登录突发与持续测试合计 22,920 次请求，零错误。

## 登录与公网入口

| 同时密码登录人数（不同模拟 IP） | P95 ms | 失败 |
| ---: | ---: | ---: |
| 1 | 89 | 0 |
| 5 | 311 | 0 |
| 10 | 540 | 0 |
| 20 | 1029 | 0 |

20 人登录档全机 CPU 约 98.5%，密码校验会短暂占满 CPU。没有发送真实邮件，没有测试验证码或 SMTP 吞吐。

公网 HTTPS `/health` 共进行了 116 次有界请求。首组 40 并发全部成功，P95 1798.67 ms；后一组 40 请求中有 23 次成功、17 次 429，触发同出口限流。10 并发档虽全部成功，P95 达 6824.75 ms，说明公网时延有明显波动。健康检查不读取业务文档，无法用这些结果推断公网业务人数。

当日源码与入口验证的限制：公网单 IP 100 请求/分钟；认证单 IP/路径默认 30 请求/分钟；登录单 IP 3 请求/10 秒；验证码邮件单 IP 3 请求/分钟；同步写入同账号至少间隔 3 秒。多人共用校园出口时会共享额度。若每人每 20 秒同步并检查一次会话，同出口约 10 人持续操作就可能碰到认证限制；这是计算情景，校园实网尚未验证。

## 带宽估算与适用范围

5 Mbps 理论为 625,000 字节/秒。假设每位活跃用户每 20 秒下载一份 90,749 字节文档，理论约 `625000 × 20 ÷ 90749 = 137.74` 人；考虑协议、其他流量和余量，先按 **80–100 活跃用户** 规划。这没有验证公网带宽饱和点。更大文档会降低容量，更低同步频率可提高在线人数。

当日客户端默认每 5 分钟同步，修改后延迟 20 秒触发同步。仅打开应用或本地学习的用户压力更低；未测注册账号总数、低频在线人数或教室真实多设备的硬上限。

## 测试边界与恢复

- 业务负载走本机回环，未经过 TLS、Caddy 和公网带宽；负载发生器也消耗这台服务器的 CPU、内存。
- 分级每档约 17 秒，持续测试仅约 61 秒，未验证数小时运行。
- 每用户使用不同有效模拟 IP，未覆盖多人共享出口、多公网发生器、真实设备和邮件。
- 第一轮诊断使用无效模拟 IP 导致共享限流，已修正并重跑；诊断轮不计入容量结论。
- 正式源码、配置、TLS、启动任务及真实用户数据库未因本次测试修改。独立测试端口已关闭，结束后生产健康检查成功、空闲内存约 715 MB；未重启服务器或购买资源。

内部脚本需要 Node >=24 和目标源码的 `server` 依赖，在自有服务器上对目标后台生成全新合成数据库；不读取生产数据库。固定口令、secret 和邮箱均是仅用于合成测试的夹具，不能配置到正式服务。正式完整模式会探测本机 4318 健康端点；`--smoke` 允许没有生产端点的开发机执行。默认测试端口 4319，可用 `CAPACITY_PORT` 指定未占用端口。输出含合成数据库和机器诊断，不应整目录公开。

```powershell
# 在源码根目录安装后台依赖（已有依赖可省略）
npm.cmd --prefix server ci
# 小规模验证：10 人约 16 秒 + 1 次登录，必须使用全新的输出目录
node scripts/capacity/server-capacity.mjs . test-results/capacity-smoke-new --smoke
# 完整分级 + 登录测试，在自有服务器上运行
node scripts/capacity/server-capacity.mjs . test-results/capacity-ramp-new
# 公网仅探测自有/获授权的 HTTPS 入口，显式指定地址
node scripts/capacity/public-probe.mjs https://your-authorized-server.example test-results/public-probe-new.json
```

内部脚本覆盖分级与登录突发；当日 200 人持续测试通过单独临时执行取得，未包含在本公开脚本内。不同版本、数据、网络与硬件重跑会产生不同结果，必须另存日期和源码哈希。
